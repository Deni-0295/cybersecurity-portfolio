# Investigation — Linux Log Analysis

## 1. Objective

Analyze Linux system logs to identify and classify:

- Authentication events.
- User sessions.
- Privileged activity.
- Scheduled tasks.
- System errors.
- Events that may require further investigation.

The objective is not to automatically classify every `failed` or `error` event as malicious activity, but to analyze each event within its context.

---

## 2. Analysis Environment

**Operating System:** Kali Linux

**Environment:** Virtual Machine

**Primary tool:**

```bash
journalctl
```

The system uses `systemd-journald` to centralize different system events.

---

## 3. Authentication Event Identification

The following command was executed:

```bash
sudo journalctl --since "7 days ago" --no-pager | grep -Ei "login|logged|session|authentication|pam_unix|lightdm"
```

A broader search was subsequently performed:

```bash
sudo journalctl --since "7 days ago" --no-pager | grep -Ei "authentication|failed|failure|success|accepted|rejected"
```

These queries helped identify authentication-related events, user sessions and failures.

---

## 4. Failed Authentication Event — LightDM

The following event was identified:

```text
Sep 27 17:59:43 kali lightdm[1128]: pam_unix(lightdm:auth): check pass; user unknown
Sep 27 17:59:43 kali lightdm[1128]: pam_unix(lightdm:auth): authentication failure; logname= uid=0 euid=0 tty=:0 ruser= rhost=
```

### Observation

The event was generated by the process:

```text
lightdm
```

and the PAM module:

```text
pam_unix(lightdm:auth)
```

The log reports:

```text
user unknown
authentication failure
```

Additionally, the field:

```text
rhost=
```

does not contain a remote source address.

### Interpretation

A failed authentication attempt occurred through the graphical login system.

The log does not provide enough information to determine who initiated the attempt or attribute it to a remote source.

Therefore, the event should be classified as:

**Failed authentication event requiring additional context.**

There is insufficient evidence in this isolated event to classify it as an attack.

## 5. Successful Graphical Session

Subsequent events showed a session being opened for the user `kali`:

```text
Sep 27 18:14:21 kali lightdm[958]: pam_unix(lightdm:session): session opened for user kali(uid=1000) by kali(uid=0)
```

The following events were also recorded:

```text
systemd-logind: New session 3 for user kali
```

And:

```text
gkr-pam: unlocked login keyring
```

### Observation

The system successfully recorded the opening of a graphical session for:

```text
user = kali
uid = 1000
```

### Interpretation

The event demonstrates a subsequent successful graphical session for the `kali` user.

However, it should not be assumed that this session was necessarily the direct result of the authentication failure recorded at 17:59:43, because the analyzed logs do not explicitly establish that relationship.

## 6. Xfce Screensaver Authentication Events

Authentication-related events were also identified in the Xfce screensaver.

Example:

```text

Sep 29 12:19:46 kali xfce4-screensaver-dialog[6207]: pam_unix(xfce4-screensaver:auth): authentication failure; logname=kali uid=1000 euid=1000 tty=:0.0 ruser= rhost= user=kali
```

### Observation

The event belongs to:

```text
xfce4-screensaver
```

The user involved was:

```text
kali
```

The log shows a password verification failure.

A subsequent event was also recorded:

```text
gkr-pam: unlocked login keyring
```

### Interpretation

These events are associated with the Xfce screensaver authentication mechanism.

The evidence shows an authentication failure followed by a keyring unlock event.

Given the graphical environment context and the involvement of `xfce4-screensaver`, the event should not automatically be interpreted as a remote access attempt.

## 12. Security Assessment

The investigation demonstrates that terms such as:

```text
failed
failure
error
authentication failure
```

are not sufficient on their own to determine whether a security incident has occurred.

Each event should be analyzed considering:

- Service that generated the event.
- User involved.
- UID.
- Terminal.
- Source address.
- Timestamp.
- Previous and subsequent events.
- Session type.
- Service status.
- Correlation with other evidence.

In this investigation:

- Graphical authentication failures were identified.
- Successful graphical sessions were identified.
- Scheduled `root` activity was identified.
- Xfce and virtualization-related errors were identified.
- No `sshd` events were found during the queried 24-hour period.

---

## 13. Indicators Requiring Further Investigation

A SOC analyst should investigate further when encountering situations such as:

- Multiple consecutive authentication failures.
- Failures originating from a remote IP address.
- Attempts targeting multiple user accounts.
- A sequence of failures immediately followed by a successful login.
- Unexpected privileged account usage.
- Session creation outside expected behavior.
- Services becoming active unexpectedly.

The available evidence in this investigation is insufficient to establish any of these situations as a confirmed security incident.

---

## 14. Conclusion

The Kali Linux journal review identified several types of system activity:

1. Graphical authentication events through LightDM.
2. Authentication failures associated with Xfce Screensaver.
3. Graphical sessions opened for the `kali` user.
4. Scheduled activity through CRON.
5. Errors related to Xfce and virtualization.
6. No `sshd` events during the reviewed 24-hour period.

The main authentication finding was a LightDM event containing:

```text
authentication failure
user unknown
rhost=
```

The log does not provide enough information to determine the origin of the attempt or classify it as malicious.

The main lesson from this investigation is:

**A failed authentication event must be analyzed within its context before being classified as a security threat.**
